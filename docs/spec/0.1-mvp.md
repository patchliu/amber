# Amber Spec 0.1-mvp

This version is a small, deliberately strict subset of the [full design](../design/AMBER_DESIGN.zh-CN.md). It is sufficient to identify a computation request and find source implementations whose **declared** contract covers it. A match is a candidate for independent verification, not a correctness certificate.

## Shape and computation

A Spec is JSON with exactly five top-level fields: `language_version`, `signature`, `domain`, `computation`, and `acceptance`. `language_version` must be `0.1-mvp`.

- `signature.inputs` and `signature.outputs` map tensor names to `{"dtype": string, "shape": [axis, ...]}`. An axis is a positive integer or a declared dimension name.
- `domain.dimensions` maps each symbolic axis to an inclusive positive integer interval `{"min": int, "max": int}`.
- `computation.nodes` is an ordered list of `{"id", "op", "inputs", "attributes"}`. Inputs can refer to signature inputs or earlier nodes. Operator identifiers begin with `amber.`. `computation.outputs` maps each signature output name to a source value.
- `acceptance` currently requires `{"relation": "semantic_contract", "reference": string}`. The reference is an identifier only; the MVP does not evaluate it.

The query side constrains each node attribute with `{"exact": value}`, `{"one_of": [value, ...]}`, or `{"any": true}`. Values are JSON strings, integers, or booleans. An implementation declaration gives concrete scalar values for its attributes. Floating JSON numbers, predicate domains, layout constraints, graph rewrites, and general equivalence are outside this version.

A query matches a declaration only if signatures, node structure, outputs, and acceptance identifiers agree; every query attribute constraint is satisfied; and the declared implementation interval contains the whole requested interval for every dimension. An undeclared required attribute returns `unknown`. A conflict returns `rejected`. Otherwise the result is `candidate`. Query `any` releases only that attribute requirement; it does not validate the result of a kernel.

The canonical Spec digest is SHA-256 over `amber:spec:0.1-mvp\n` followed by UTF-8 JSON with sorted keys and no extra whitespace. Object key order does not matter. Ordered node and shape arrays retain their order. This is the MVP identity format, not a promise that it matches the final language's future digest scheme.

## Local registry API

Run `python -m amber_house --root .amber-local --port 8000`.

| Request | Body or result |
| --- | --- |
| `POST /v1/specs/compile` | `{"spec": Spec}` → canonical Spec digest |
| `POST /v1/implementations` | `{"spec": concrete Spec, "target": {"backend": string, "architecture": string}, "source": UTF-8 text}` → implementation and source digests |
| `POST /v1/queries` | `{"spec": query Spec, "target": target}` → reports and `cache: hit` or `miss` |
| `GET /v1/artifacts/{source_digest}` | Source bytes after published manifest check and digest verification |
| `GET /health` | Service status |

The server uses SQLite for manifests, catalog revision, and query cache. A new upload atomically increments the catalog revision; an identical re-upload leaves it unchanged. Source bytes live under `blobs/` by SHA-256. The client verifies the downloaded digest before adding it to a local content cache. The local service binds to loopback by default and is intended for one server process per registry directory. Authentication, multi-tenant policy, evidence validation, device execution, and remote federation remain future work.

The architecture document uses a broader `0.1` proposal and a richer YAML request. That YAML is illustrative and is not accepted by this narrower MVP endpoint.
